# Core — Architecture

## Entry Point: `AppSuiteApplication`

`AppSuiteApplication.cs` (~6000 lines) is the abstract singleton base class every consumer application must subclass. It manages:
- Application lifecycle (startup, shutdown, restart)
- Configuration and theming (light/dark, accent color)
- Window management and dialog orchestration
- Logging (NLog), auto-update, permissions, pro-version activation
- Privacy policy / user agreement enforcement
- External dependency management and script execution

Platform-specific logic is split into partial classes:
- `AppSuiteApplication.Windows.cs`
- `AppSuiteApplication.MacOS.cs`
- `AppSuiteApplication.Linux.cs`

The interface `IAppSuiteApplication` provides the abstraction; `IAppSuiteApplication.Current` is the static singleton accessor.

### Shutdown Reason

`Shutdown(int delay, ApplicationShutdownReason reason)`, the 3-argument `Restart(..., ApplicationShutdownReason reason)`, and the overridable `OnPrepareShuttingDownAsync(ApplicationShutdownReason reason)` carry an `ApplicationShutdownReason` describing *why* the app is shutting down (`None`, `Critical`, `UpdatingApplication`). It replaces the former `isCritical` boolean: "critical" is now `reason == ApplicationShutdownReason.Critical`, which still means asynchronous shutdown preparation is not allowed (`OnPrepareShuttingDownAsync` must complete synchronously). `UpdatingApplication` is set by `ShowAppUpdateDialogAsync` before shutting down to apply an auto-update, letting a subclass react in `OnPrepareShuttingDownAsync` (e.g. releasing files that the external auto-updater must replace). The active reason is also exposed as the read-only `[ThreadSafe]` `ShutdownReason` property (`None` until shutdown starts), raising `PropertyChanged` when set. It is captured on the first `ShutdownAsync` call when the reason is non-`None`; a later call that escalates an in-progress shutdown to `Critical` overwrites it, keeping it consistent with `IsCriticalShutdownStarted`. When the shutdown closes main windows, the first `ShutdownAsync` call closes them and returns early *before* preparing, deferring `OnPrepareShuttingDownAsync` to a second `ShutdownAsync` triggered once the last window has closed (`OnMainWindowClosedAsync` → `Shutdown`). That deferred call re-threads the captured `ShutdownReason` into the `reason` parameter, so a subclass reading the `OnPrepareShuttingDownAsync(reason)` parameter sees the original reason (e.g. `UpdatingApplication`) rather than `None` even on the multi-window path — reading the parameter and reading the `ShutdownReason` property are therefore equivalent there.

### Restart After System Reboot (Windows)

The framework relaunches the app after a Windows system reboot using a `RunOnce` registry entry. `RunOnce` is used in place of `RegisterApplicationRestart` because the OS-level "Restart apps" sign-in setting is off by default on most installs, which makes `RegisterApplicationRestart` unreliable in practice.

The relaunch is always-on for AppSuite-based applications on Windows. The `RestoreMainWindowsAfterSystemReboot` property is a separate, orthogonal concern: when `true`, the relaunch command line includes the `-restore-main-windows` argument so that main windows are restored on the next run; when `false`, the app is still relaunched but without window restoration.

Lifecycle:
1. **On launch** (during `OnPrepareStartingAsync`): any stale entry left from a previous shutdown is removed via `RemoveRunOnceEntryForRestartOnWindows()`. Defensive cleanup — under normal flow `RunOnce` self-deletes when it fires, so this is usually a no-op.
2. **On OS-initiated shutdown** (Avalonia's `ShutdownRequested` event fires — i.e. `WM_QUERYENDSESSION`): the handler sets `shutdownSource = System` (matching the macOS behavior) and calls `WriteRunOnceEntryForRestartOnWindows()`, which writes an entry to `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` pointing at the current exe with the `-restarted-by-system` argument always appended, plus `-restore-main-windows` when `RestoreMainWindowsAfterSystemReboot == true`. The entry name is `CarinaStudio.<AssemblyName>.RestoreAfterReboot`, namespaced by assembly name so multiple AppSuite-based apps do not collide.
3. **On graceful, app-initiated shutdown** (`ShutdownAsync` called with a non-`Critical` reason *and* `shutdownSource == ShutdownSource.Application` — e.g. File → Exit, in-app `Restart()`): the entry is removed via `RemoveRunOnceEntryForRestartOnWindows()`. Critical shutdowns skip cleanup. **Importantly**, OS-initiated shutdowns also reach `ShutdownAsync` (Avalonia drives it after `ShutdownRequested`) but their `shutdownSource == ShutdownSource.System` — the cleanup must be skipped there, otherwise the entry just written in step 2 would be wiped before reboot.
4. **On next login** (when an OS shutdown actually proceeded): Windows fires `RunOnce` once and auto-deletes the entry. The app launches with `-restarted-by-system` (and optionally `-restore-main-windows`). The argument parser sets `LaunchOptionKeys.IsRestartedBySystem`, and if `-restore-main-windows` was included, `IsRestoringMainWindowsRequested` drives main-window restoration.
5. **Duplicate suppression for late system relaunch**: Windows can take minutes to fire `RunOnce` after sign-in. If the user manually launches the app before that, the system-fired instance will arrive later and find an existing multi-instance server already running. `SendArgumentsToMultiInstancesServer` short-circuits when `LaunchOptionKeys.IsRestartedBySystem == true` — it connects to verify the server is alive, then returns without forwarding the args (which would otherwise inject `-restore-main-windows` into the user's already-open session and trigger redundant window restoration). The late instance silently shuts down; the user's session is untouched.

Force-kill paths (Task Manager → End Process, `taskkill /F`, antivirus, crash) bypass both hooks: nothing is written if no shutdown was in progress, and if a force-kill occurs *during* an OS shutdown the entry survives, which is correct because the user did request the reboot.

**Known limitation — cancelled system shutdown.** If `WM_QUERYENDSESSION` fires (entry written, `shutdownSource` becomes `System`) and the shutdown is then cancelled by another app, `shutdownSource` is sticky and subsequent app-initiated graceful exits will *also* see it as `System` — so the cleanup branch in step 3 is skipped and the stale entry survives until either (a) the next system reboot consumes it, or (b) the launch-time cleanup in step 1 removes it on a manual relaunch. In the meantime, a spurious relaunch may occur on the next login. This trade-off is accepted: gating cleanup on `shutdownSource` is what makes the primary case (system reboot relaunches the app) work correctly.

All registry operations are best-effort and exception-safe; failures never propagate.

### Application Data Directory & Restart

**Source-build detection.** The static field `IsRunningFromSourceBuild` (set in the static constructor) is `true` when `AppContext.BaseDirectory` contains a `bin/Debug/` or `bin/Release/` path segment — i.e. the app is running from a build-output folder (IDE run such as Rider, `dotnet run`, or a locally-built binary run in-place) rather than a shipped/installed layout. It is a **path heuristic**, not a host check: it is derived from `AppContext.BaseDirectory` (which is the assembly's directory under *both* an apphost launch and a `dotnet App.dll` launch — the old `MainModule`/`GetModuleFileName`/`CodeBase` probing and the `== "dotnet"` executable-name test were removed because a launcher-execed apphost defeats them). A shipped macOS `.app` runs from `…/Contents/MacOS/` and an installed Win/Linux app from its install dir, so neither matches; the one caveat is running a *packaged* app directly from its build-output folder before it is moved/installed.

**Data directory (`AppDataDirectoryPath`).** Selected once in the static constructor and exposed as `RootPrivateDirectoryPath`:
- **macOS** — `~/Library/Application Support/Carina Studio/<AssemblyName>`, with a `-Debug` suffix appended when `IsRunningFromSourceBuild` (so dev sessions never read/write the production data folder). The directory is created eagerly here.
- **Windows / Linux** — `AppContext.BaseDirectory` (trailing separator trimmed; the value is compared with `PathEqualityComparer`, so it must stay separator-free), i.e. the app's own directory alongside its assemblies.

`InitSettingsFilePath` and `SettingsFilePath` are combined from `AppDataDirectoryPath` in the same static constructor (they must be assigned there, after the directory is chosen, not via field initializers — static field initializers run in textual/alphabetical-declaration order, before the directory would be known).

**Restart executable selection.** In the shutdown/restart path, `useDotnetHost` decides how to relaunch:
```
useDotnetHost = IsRunningFromSourceBuild || <Environment.ProcessPath ends with the dotnet host name>
```
- When **true**, the app is relaunched through the shared dotnet host: the managed assembly path is extracted from the first token of `Environment.CommandLine` (quote/space aware, so spaced paths survive) and the process is started as `dotnet "<assembly.dll>" <restartArgs>` (`FileName = "dotnet"` on Win/Linux; `exec dotnet …` inside the macOS `nohup` relauncher). This requires `dotnet` to be resolvable on the relaunch child's PATH — satisfied under Rider/terminal; it can fail for an apphost launched with a minimal PATH (e.g. a Finder double-click of the `bin/Debug` binary).
- When **false** (the shipped case: self-contained apphost, `IsRunningFromSourceBuild` false and `ProcessPath` not the dotnet host), the app re-execs its own `Environment.ProcessPath` with `restartArgs` — no PATH dependency.

The `ProcessPath`-ends-with-dotnet leg additionally covers a framework-dependent install launched via `dotnet App.dll` from a non-`bin` path, where the source-build heuristic alone would be false.

### Default Font Configuration

Three cooperating pieces, all deriving the font family list from `GetDefaultFontFamilyName(CultureInfo preferredCultureInfo)`: a **composite font family name** (comma-separated primary + fallback chain) with `Inter` as the Latin face followed by every embedded CJK face, ordered by how likely the user is to be reading that script.
**How the ordering is built.** The function takes the *preferred* culture (the application culture, with `ApplicationCulture.System` already resolved) and consults `ApplicationCulture.System.GetCultureInfo()` for the system culture, because the two answer different questions: the preferred culture says which script the UI is in, the system culture says which script the user reads when the UI language doesn't tell us. It assembles a culture list — preferred first, then the system culture if it contributes a script the preferred culture doesn't — then appends `ja-JP` / `zh-CN` defaults for any script still missing, so **every chain ends up containing all CJK faces** with the most relevant one first. Concretely: `ja-JP` on a `zh-TW` system yields `Inter, JP, TC, SC`; `zh-TW` on any system yields `Inter, TC, SC, JP`; `en-US` on a Japanese system yields `Inter, JP, SC, TC`; a non-CJK system yields `Inter, JP, SC, TC`. An explicit Chinese preference is never overridden by a differing system Chinese variant. Script detection lives in the `extension(CultureInfo)` block of `CultureInfoExtensions` (`IsChinese`, `IsJapanese`, `ChineseVariant`), all matching on the language prefix **without** a region dash so neutral cultures (`ja`, `zh` — reachable on Linux via `LANG=ja`) classify correctly.

1. **`FontManagerOptions.DefaultFamilyName`** (in `BuildApplication`, from `_LaunchCultureInfo`) — a backstop only, immutable after the `FontManager` is created. The per-codepoint fallback follows the composite chain only when the *control's own* `FontFamily` is that composite; text carrying `$Default` (or Fluent's stock `fonts:Inter#Inter, $Default`) falls through to the **system** font collection, where the OS language — not the app setting — picks the CJK face (e.g. PingFang on macOS). So this option alone cannot deliver culture-correct CJK.

2. **`ContentControlThemeFontFamily` resource override — the load-bearing piece.** Set in `OnFrameworkInitializationCompleted` and re-assigned inside `UpdateCultureInfoAsync` whenever the composite name changes. Fluent's ControlThemes bind `FontFamily` of every TopLevel (`Window`, `PopupRoot`, `OverlayPopupHost`, `EmbeddableControlRoot`) to this resource via `DynamicResource`, so all controls inherit the composite, CJK fallback honors the culture ordering, and re-assigning the resource re-shapes text live. **Culture changes therefore need no app restart** — the old restart flow (`ApplicationOptions.IsChineseVariantChanged`, the `MainWindow` notify-then-`Restart()` dialog, `RestartApplicationNeeded` from the options dialog, and the `*.ChineseVariantChanged` string keys) was removed; consumer apps must drop their corresponding warning `TextBlock`s on upgrade. The re-assignment is gated on the **font family name** changing, tracked by the `defaultFontFamilyName` field, not on `ChineseVariant` changing — an en-US → ja-JP switch leaves the Chinese variant untouched and would otherwise never re-shape text. `IAppSuiteApplication.LaunchChineseVariant` still reports the launch-fixed value backing item 1. `SplashWindowImpl` styles its text from the same resource.
   **Ordering caveat — only the first CJK face in the composite affects selection, still true on Avalonia 12.0.4.** Keep the composite's first segment in a collection with **no CJK glyphs** (`fonts:Inter`), so that the first *CJK* segment is the one Avalonia consults. That segment is honored. Everything after it is not: once the first CJK face lacks the glyph, matching abandons the composite and resolves the codepoint by an *unordered* scan of the whole `fonts:Noto` collection, which deterministically lands on `Noto Sans SC`. This is measured, not inferred — `DefaultFontsTests.FallbackFontSelectionTest` renders `业` (U+4E1A, present in SC and TC, absent from JP) and shows `Inter, JP, TC, SC` → SC even though TC has the glyph and precedes SC, and `Inter, JP` alone → SC even though SC is not in the chain at all; its companion assertion `Inter, TC, SC` → TC confirms first position *is* honored. The same mechanism is what broke a `fonts:Noto#Noto Sans`-first composite.
   **On PR #21435:** Avalonia 12 ships it (deterministic, coverage-checked, culture-aware matching), and it does fix first-position selection — but it does **not** make positions two-plus of a composite ordered, as the test above demonstrates on 12.0.4. Earlier revisions of this section claimed otherwise; that claim rested on assertions using `骨`, which is present in JP, SC *and* TC and therefore only ever exercises the first position. Any future re-test of this behavior must use a character absent from the leading face.

   **Consequence:** the fall-back ordering that `GetDefaultFontFamilyName` computes past position one — the system-variant-driven `TC, SC` vs `SC, TC` tail on Japanese chains, and the trailing `JP` on Chinese chains — is **inert** at runtime. It is kept because it costs nothing, it documents the intended preference, and it starts working the moment matching becomes ordered. `FallbackFontSelectionTest` is written as a tripwire: it is *expected to fail* when that happens, at which point revisit this section and re-point the assertions at the ordered behavior.

3. **Vertical-metrics normalization** (`Media/MetricsNormalizedFontCollection` + `Media/FontVerticalMetricsNormalizer`) — registered for `fonts:Noto` in `AddEmbeddedFontCollections` (shared by the app builder and `Core.Tests`). Noto Sans JP/SC/TC natural metrics (hhea 1.16 / 0.29 em → 1.45 em) exceed the ~1.3 em explicit `LineHeight` used by the styles, and Avalonia's `TextLineImpl` handles that by clamping with `baseline = -ascent` — all the loss comes off the bottom, making CJK-only lines top-heavy; it centers only when `LineHeight` > natural height. So the font files listed in `AppSuiteApplication.MetricsNormalizedFontFileNames` get their **bytes patched in memory at load time**: `hhea` plus `OS/2` typo/win metrics are rewritten to Inter's ratios (ascent 0.96875 em, descent 0.24121 em, lineGap 0, computed from each font's own `unitsPerEm`), `USE_TYPO_METRICS` is set, and table checksums plus `head.checkSumAdjustment` are recomputed — every backend (CoreText, FreeType, DirectWrite, HarfBuzz) then reports identical metrics, CJK lines center exactly like Latin ones, and mixed-script baselines align. The shipped TTFs stay byte-identical, so the OFL "Noto" reserved-name clause is never triggered. The collection is a thin `FontCollectionBase` subclass built on Avalonia 12's public API: it enumerates the source's font assets via `AssetLoader.GetAssets` (filtering `.ttf`/`.otf` itself — `FontFamilyLoader` is internal in 12), patches the selected files, and registers each stream through the public `TryAddGlyphTypeface(Stream, …)` — no reflection into Avalonia internals. Explicit `LineHeight` styles at the `TextBlock` layer remain the app-wide density knob.

**Changing or adding an embedded font — checklist:**

1. Put the font file under `Core/Fonts/<Collection>/` and add an `<AvaloniaResource>` entry in `Core.csproj`. Only plain single-face `.ttf`/`.otf` is supported by the normalizer (`0x00010000` or `OTTO` sfnt); `.ttc` collections would need `FontVerticalMetricsNormalizer` extended first.
2. If the face has tall CJK-style metrics and participates in default text, add its file name to `AppSuiteApplication.MetricsNormalizedFontFileNames` — normalization is family-agnostic (targets are ratios applied to the font's own `unitsPerEm`), so no other constants change.
3. If it should participate in default text, add its family to `GetDefaultFontFamilyName` — a `XXFontFamilyNames` constant plus the branches that emit it (see *Adding a new culture* below), keeping `fonts:Inter#Inter` as the first segment. Remember that only the **first** CJK face is honored (ordering caveat above), so a face that is never emitted in first position for some culture is effectively unreachable for that culture today.
4. A new collection URI must be registered in `AddEmbeddedFontCollections` (never inline in `BuildApplication` — tests rely on the shared method).
5. Expose it from `Fonts/Media/BuiltInFonts.cs` (a separate project — see `Fonts/AGENTS.md`): backing field, `FontFamily` property, entry in `FontFamilies`, and — for a face under `Core/Fonts/Noto/` — the `nameof(...)` arm of the Noto group in `OpenStream`. All four lists are alphabetical. The `#if DEBUG` static initializer then validates the addition for free: it walks every public `FontFamily` property, throws if a family loaded no typefaces, and opens each font's stream, so a Debug build failing here means the resource URI or file name is wrong.
6. Update/re-run `Core.Tests/DefaultFontsTests.cs` (`dotnet test Core.Tests`; Debug-only — test cases and the test runner are excluded from the Release build since `Core.Tests` is itself released as a library package providing testing infrastructure to consumer applications), which guards: normalized metrics (Regular + Bold) matching Inter's ratios, Latin-only vs CJK-only line height *and* baseline equality, culture-ordered face selection for `骨` (`CjkVariantChar` — covered by all CJK faces, glyph differs between them), the first-face-only fall-back behavior via `业` (`CjkFallbackChar`), and live culture switching via the resource. Finish with a visual pass over the line-height rows in the `Tests` app.

## Adding a New Application Culture

Every step below was exercised by the `ja-JP` addition; follow it in order. Steps 1–4 are the minimum for a culture that needs no new font.

**1. Declare the culture.** Add the value to `ApplicationCulture` (`Core/ApplicationCulture.cs`). Declaration order is user-visible: `ApplicationOptions.Cultures` iterates `Enum.GetValues<ApplicationCulture>()`, so the enum order is the order of the language ComboBox.

**2. Add string resources.** Create `Core/Strings/<name>.axaml`, plus `<name>-Linux.axaml` / `<name>-OSX.axaml` if the platform overrides in `Default-Linux.axaml` / `Default-OSX.axaml` need translating — `UpdateStringResources` loads all three by `cultureInfo.Name`, and the Avalonia SDK globs `**/*.axaml` automatically, so **no `Core.csproj` entry is needed**. Then add the `String/ApplicationCulture.<VALUE>` display name to *every* string file, including the existing locales, since each language names all the others. Mirror the key set of `zh-TW.axaml`: the eight pure-format keys it omits (`CpuUsage.Format`, `GCFrequency.Format`, the three `Screen.*.Format`, `Version`, `ScriptLanguage.JavaScript_ES_5_1`, `ScriptLanguage.Python_3_4`) stay untranslated. Do the same for `SyntaxHighlighting/Strings/<name>.axaml` and add the matching branch to `UpdateStrings` in `SyntaxHighlighting/Controls/SyntaxHighlighting.cs`, inside the existing `#pragma warning disable IL2026` region.

**3. Wire document selection.** Add a branch to `DocumentSourceExtensions.SetToCurrentCulture` (`Core/DocumentSource.cs`) so agreement / change-list documents resolve to the new culture when the app is running in it, falling back to `EN_US` when the `DocumentSource` doesn't offer it.

**4. Update the self-test.** `Core/Testing/Common/LocalizationTest.cs` enumerates every enum value and throws if one has no entry in `TestStrings`, so add the culture and its expected `LocalizationTest.String` value there, plus a case in the `appCultures[0]` ordering switch that reverses the list when the culture matches the system culture. Also add the culture to `Tests/App.axaml.cs` document sources and the cycle in `Tests/MainWindow.axaml.cs` if you want to exercise it in the test app.

**5. If the culture needs its own font**, additionally:
   - Embed the faces per *Changing or adding an embedded font* above — that checklist covers the asset, `<AvaloniaResource>`, `MetricsNormalizedFontFileNames`, and exposing the family from `BuiltInFonts` in the `Fonts` project.
   - Add an `IsXxx` extension property to the `extension(CultureInfo)` block in `Core/CultureInfoExtensions.cs`, matching on the language prefix **without** a region dash so neutral cultures classify correctly. Keep the block's members alphabetical.
   - In `GetDefaultFontFamilyName`, add an `XXDefaultCultureName` constant, an `XXFontFamilyNames` constant, an `else if` in the culture-list stage (mark the script as present and add the system culture when it supplies it), a matching `else if` in the font-list stage, and a tail `if (!hasXxCultureInfo)` that appends the default culture. All four edits follow the existing JA/ZH pairs.
   - Extend `Core.Tests/DefaultFontsTests.cs`: the culture's expected face in `CultureFontSelectionTest`, a CJK sample string in `ConsistentLineMetricsTest`, the family name in `NormalizedVerticalMetricsTest`, and a step in `DynamicCultureFontSwitchingTest`.

**6. Consumer applications.** Adding a culture to `Core` makes it appear in every app's language list. An app without its own resources for it must override `CheckApplicationCultureSupport` to return `false` for that value — `ApplicationOptions.Cultures` filters the ComboBox on it, and `UpdateCultureInfoAsync` falls back to `ApplicationCulture.System` with a warning if the setting still holds an unsupported value.

## Backdrop System

`BackdropTarget`, `Backdrop`, and the `BackdropEffect` enum (in `Controls/`) implement a manual "frosted glass" backdrop: a `BackdropTarget` snapshots its scrollable content into a bitmap, and one or more `Backdrop` overlays sample + blur the region behind themselves from it.

**`BackdropTarget`** is a `Decorator` wrapping the content (typically a `ScrollViewer`). It lazily renders its `Child` into a **single shared** cached `RenderTargetBitmap` (`PrepareBackdrop`), reused by every registered consumer. `internal DrawBackdrop(context, consumer, srcRect, destRect)` is called by a consumer during its render: `srcRect`/`destRect` are in the **consumer's** coordinate space, and the target maps `srcRect` into the bitmap's **pixel** space (Skia's `DrawImage` samples the source rect in pixels, not DIPs) before blitting.

- **Fixed 96-DPI snapshot (hard constraint).** `RenderTargetBitmap.Render` uses `ImmediateRenderer` (not the compositor) and **corrupts any content that has a `BoxShadow` unless the bitmap DPI is exactly 96** — the blur leaks a scale onto following siblings. So the snapshot is always created at `new Vector(96, 96)`; HiDPI-sharp and reduced-resolution snapshots are impossible while box-shadowed content must render correctly (verified empirically — both up- and down-scaling corrupt). On HiDPI this means the backdrop is captured at DIP resolution and upscaled when drawn (soft), which the blur hides.
- **Invalidation.** Auto-invalidation listens for the **bubbling** `ScrollViewer.ScrollChangedEvent` (one handler on the target catches any descendant scrollable — `ScrollViewer`, `ListBox`, nested — and `ScrollChanged` fires on offset **and** extent/viewport changes, so item add/remove is covered too), gated by the `AutoInvalidate` property. `OnSizeChanged` and the public `Invalidate()` also trigger it. `SceneInvalidated` was deliberately **not** used: `CompositingRenderer` always reports a full-window `DirtyRect` with no locality, so it cannot scope to a consumer.
- **`BackgroundColor`.** A `Color` filled (via a cached `ImmutableSolidColorBrush`) behind the snapshot inside `DrawBackdrop`, so a `Backdrop`'s blur samples a real color instead of transparency where the snapshot does not cover — e.g. at content-boundary edges, which otherwise make the blur fade. Changing it repaints consumers (`InvalidateConsumers`) **without** dropping the cached snapshot.

**`Backdrop`** is a `Decorator` that draws the blurred backdrop behind its own content. It hosts an internal `BackdropLayer` visual (added to `VisualChildren` *before* `Child`, which `Decorator` appends) carrying an `ImmutableBlurEffect`; the layer draws the sampled backdrop and the blur applies to it alone, keeping `Child` sharp (`DrawingContext` has **no** inline blur — blur must be a `Visual.Effect`). The `BackdropLayer` (not the `Backdrop`) is the registered consumer; the `Target` property connects it to a `BackdropTarget`.

- **`BackdropEffect`** (the enum, exposed as the `Backdrop.BackdropEffect` property — named so to avoid colliding with `Visual.Effect`; `Blur` / `LensBlur` / `None`, default `None`): `None` draws nothing; `Blur` samples the region directly behind; `LensBlur` samples a *larger* region (inflated `srcRect`) into the same dest. Both inflate the sampled region by `BlurRadius` on all sides so the blur has real content at the edges instead of fading — the layer does not clip to bounds, so the over-draw is included in the effect's input bounds.
- **GPU-only.** Drawing is skipped on the software/CPU pipeline (snapshot+blur is only worthwhile on the GPU). The public static `Backdrop.IsSupported` detects this by **reflecting** the internal `AvaloniaLocator.Current` for a registered `IPlatformGraphics` (those members are `internal` in the ref assembly but `public` at runtime, so the reflection uses `Public | NonPublic`; the result is cached; fail-fast on Avalonia upgrade). `IsBackdropEffectActive` (read-only `DirectProperty`) = `Target != null && BackdropEffect != None && IsSupported && isBackdropEffectEnabled` (the last factor is the `EnableBackdropEffect` toggle below). `ApplicationOptions.IsBackdropEffectSupported` ANDs `Backdrop.IsSupported` with the `EnableBackdropEffect` configuration, so an options UI can hide the backdrop strength setting both where the pipeline is unsupported and where the effect has been turned off.
- **`EnableBackdropEffect` (runtime on/off).** `ConfigurationKeys.EnableBackdropEffect` (`bool`, default `true`) globally enables/disables the effect. When `false`, `RenderBackdrop` short-circuits (draws nothing) and `IsBackdropEffectActive` reports `false`. `Backdrop` reads the flag on attach — falling back to the key's default value when no `IAppSuiteApplication` singleton is present — and subscribes to `Configuration.SettingChanged`; a runtime change re-evaluates the flag and invalidates the **`BackdropLayer`** (not the `Backdrop` decorator, which draws nothing itself), so the surface repaints immediately. The subscription is removed on detach.
- **`Strength` → internal layer opacity (`DefaultBackdropEffectStrength`).** `Strength` (`StyledProperty<double>`, range `[0, 1]`, coerced) is the public knob for backdrop visibility. It **default-binds to the `SettingKeys.DefaultBackdropEffectStrength` setting** (`double`, default `0.5`): on attach the setting value is applied to `Strength` via `SetValue(StrengthProperty, …, BindingPriority.Style)` (re-applied on setting change; the disposable token is cleared on detach to avoid pinning the control alive). `Style` priority sits *below* `LocalValue`, so an explicit `Strength` value/binding on the consumer wins. `Strength` maps **non-linearly** to the **`BackdropLayer`'s** `Opacity` via `UpdateBackdropLayerOpacity()` (called from the constructor and on `Strength` change): `Math.Pow(strength, LayerOpacityGamma=0.8) * MaxLayerOpacity=0.5`, i.e. effective opacity range `[0, 0.5]`. The opacity lives on the **layer**, not the `Backdrop` decorator, so a consumer-set `Opacity`/`OpacityMask` on the `Backdrop` composes independently. `BackdropLayer.Render` **skips** the snapshot+draw work when its `Opacity <= 0` (strength 0); this is safe because `Opacity` is an `AffectsRender` property in Avalonia, so changing it re-records the layer's draw list on the next frame — no manual `InvalidateVisual` is needed. The control clamps the setting to `[0, 1]`, and `ApplicationOptions.DefaultBackdropEffectStrength` (label *"Backdrop Effect"*) now also exposes the full `[0, 1]` range — the earlier narrowed UX bounds (`Min/MaxDefaultBackdropEffectStrength` = `[0.25, 0.75]`) were **removed**, since the `Backdrop` maps strength to opacity itself.

**Effect z-order caveat.** A visual carrying a live `Effect` does **not** reliably respect child z-order in the 11.3 compositor — the blur layer composites *over* an immediately-following sibling (effects are queued as deferred commands, not applied in simple child order). So an overlay meant to sit *on top* of the blur (tint/frame) must be placed **behind** the `Backdrop` and shown through its transparency (the `Strength`-driven layer opacity — lower `Strength` lets more of the tint show through), not stacked in front of it.

## Theming: Selectors for StyleKey-Overriding Controls

Several custom controls override `StyleKeyOverride` to a base Avalonia type (e.g. `TabItem`, `TabControl`, `ListBox`) so they receive the Fluent `ControlTheme` — Avalonia (verified on 12.0.4) resolves control themes by exact style key with **no base-type fallback**, so removing such an override strips the Fluent theme (foreground pseudo-classes, padding baselines) entirely.

Style selectors match a control's **StyleKey**, not its CLR type. The Avalonia 11 XAML compiler masked this by substituting a selector's target type with its compile-time `StyleKeyOverride`; the Avalonia 12 compiler does not, so a derived-type selector like `controls|TabItem` compiles to the derived type and **silently never matches** — the control just falls back to the Fluent template (this is how the TabItem header font size regressed during the Avalonia 12 upgrade).

Convention (see the `TabItem` styles in `Themes/Base-Styles.axaml`): write the selector against the **style key type** (`Selector="TabItem"`), and put `TargetType="controls:TabItem"` on the inner `ControlTemplate` so `TemplateBinding`s to the derived control's properties still compile. A narrower template `TargetType` than the selector type is accepted by the compiler and is safe as long as only the derived control is used with that style in practice.

## Window Chrome: Drawn Decorations (Avalonia 12)

Avalonia 12 **removed** the `Avalonia.Controls.Chrome.TitleBar` and `CaptionButtons` controls, the `VisualLayerManager.ChromeOverlayLayer`, and the `Window.ExtendClientAreaChromeHints` property. Managed (non-system) window chrome is now modeled by `Avalonia.Controls.Chrome.WindowDrawnDecorations`: a logical element attached to the window whose `Template` produces a `WindowDrawnDecorationsContent` with three slots — `Underlay` (below client content: borders/background/drag region), `Overlay` (above client content: caption buttons), and `FullscreenPopover` (hover title bar in fullscreen). `TopLevelHost` extracts those visuals and inserts them into its own tree, so the **`Window` `ControlTemplate` no longer hosts any chrome** — it is just the background + `PART_ContentPresenter` (do not re-add a title bar there).

AppSuite supplies its own decorations in `Themes/Base-Styles.axaml` (`Styles.Resources`):
- **`Theme/WindowDrawnDecorations.ExtendedClientArea`** — a `ControlTheme` for `WindowDrawnDecorations`. Its `Overlay` holds **only the caption buttons (no title `TextBlock`)** — this is deliberate: AppSuite extended windows show the tab strip in the title-bar region, and the window title must not appear. Buttons are the standard four (`PART_FullScreenButton` hidden by default, `PART_MinimizeButton`, `PART_MaximizeButton` with `RestoreButtonPath`, `PART_CloseButton`), each carrying `WindowDecorationProperties.ElementRole` (`MinimizeButton`/`MaximizeButton`/`CloseButton`/…) — the framework wires actions by that attached property + `PART_*` name, replacing the old `PART_*`-only convention. `:maximized` swaps the restore glyph; `:not(:has-minimize)`/`:not(:has-maximize)`/`:fullscreen` hide parts; `HasTitleBar` gates the whole overlay so **macOS keeps its system traffic-lights** (managed title bar disabled there) instead of drawing duplicate buttons. Frame/shadow thickness are 0 (AppSuite draws its own window background).
- **`Theme/CaptionButton`** — the button `ControlTheme` used by the above, themed with `Brush/CaptionButtons.Button.{Background.PointerOver,Background.Pressed,Foreground}` (the `Foreground` brush is theme-aware for light/dark glyphs).

The theme is applied **only to windows extending the client area**, via `Selector="Window[ExtendClientAreaToDecorationsHint=True]"` setting `Window.WindowDecorationsTheme`. Only `MainWindow` extends (`IsExtendingClientAreaAllowed` → `UpdateExtendingClientArea`); dialogs do not, so they keep normal system chrome (and `WindowExtensions.HideCaptionButtons`, which uses native Win32 `WS_SYSMENU` removal / macOS `NSWindow` APIs — unaffected by this migration). `TabControl` reserves `ExtendedClientAreaWindowConfiguration.SystemChromeWidth` (135 on Windows = 3×45, 80 on macOS) on the caption side for the buttons, plus `Double/TabControl.TabStrip.ExtendedClientAreaReserveSpace` (40) on the opposite end as a window-drag area — the drag reserve is dropped when `WindowState == FullScreen` (nothing to drag), and the margin re-evaluates on `WindowState` changes because `IsSystemChromeVisibleInClientArea` no longer flips on macOS fullscreen transitions. `MainWindow.UpdateExtendClientAreaChromeHints` is an AppSuite macOS-only helper (thick title bar + `NSWindow` title visibility), **not** the removed Avalonia property.

## macOS Full-Screen Window Controls (Traffic Lights)

In native macOS fullscreen the system relocates the title bar (with the traffic-light buttons) into an auto-hiding overlay window, so extended-client-area windows would show no window controls. `Native/FullScreenWindowControls.cs` re-creates them inline, JetBrains Runtime-style (`AWTWindow.m` is the reference implementation); `ExtendedClientAreaWindowConfiguration.IsSystemChromeVisibleInFullScreen` is therefore `Platform.IsMacOS`, and consumer apps' existing inset bindings reserve the left 80 pt in fullscreen automatically.

One controller instance per `MainWindow`, created alongside the `nsWindow` field in `UpdateExtendClientAreaChromeHints` and disposed in `OnClosed`. Mechanism:

- A runtime-defined `NSView` subclass (`Class.DefineClass`, name `CarinaStudioFullScreenWindowControlsView`) is both the notification observer and the button container; the owning controller is bound via `Class.TrySetClrObject` (requires `CarinaStudio.AppBase.MacOS` ≥ 2.4.4.722 — earlier versions had a broken ivar read that crashes with `AccessViolationException`).
- On `NSWindowDidEnterFullScreenNotification`: locate the relocated original buttons via `standardWindowButton:`, verify their host window class is `NSToolbarFullScreenWindow` (**private class name — deliberate fail-fast tripwire**), hide that overlay's content view, then create fresh buttons with `+[NSWindow standardWindowButton:forStyleMask:]` inside the container, pinned top-left in `contentView` via autoresizing mask. Reversed on `NSWindowWillExitFullScreenNotification`.
- **Button geometry matches the windowed thick title bar**: captured live (height + per-button frames, static cache) at construction and on every `NSWindowWillEnterFullScreenNotification` while the window is still windowed (only when the bar is actually thick, height ≥ 30); falls back to measured constants (38 pt bar, 13 pt left inset, vertically centered) when a window restores directly into fullscreen before any capture.
- **Idle/hover rendering mirrors JBR**: manufactured buttons cannot be trusted to render idle state, so when the mouse is outside the container all three buttons are hidden and the container's `drawRect:` override draws neutral 12 pt circles (`NSBezierPath` filled with `NSColor.TertiaryLabel`, theme-adaptive). On `mouseEntered:` (via `NSTrackingArea`, `InVisibleRect`) close/zoom are shown and `setHighlighted:`; the container also overrides `_mouseInGroup:` (**private selector**) so the hover glyphs (×/−/⤢) render. The miniaturize button stays a gray circle and `IsEnabled = false` — windows cannot minimize in fullscreen.
- In fullscreen `TitleVisibility` now stays `Hidden` (the old force-`Visible` workaround that surfaced the title in the system overlay was removed — the overlay is suppressed).

Known AppBase caveat: the `NSView.Frame` **setter** throws (`Property` metadata misreports `frame` as read-only as of AppBase 2.4.4.722) — send `setFrame:` through a `Selector` instead; getters are fine.

## Key Namespaces

- **`Controls/`** — 90+ custom Avalonia controls: dialogs (agreement, file selection, app update), `MainWindow` base classes, `TutorialPresenter`, `NotificationPresenter`, specialized input controls.
- **`ViewModels/`** — MVVM view models: `ApplicationOptions`, `ApplicationInfo`, `ApplicationUpdater`, `MainWindowViewModel`. All extend `ViewModel<TApp>`.
- **`Data/`** — Profile system: `BaseProfile<TApp>`, `BaseProfileManager`, `IProfileManager`. Profiles are JSON-serialized; persistence uses an IO task factory for thread safety.
- **`Scripting/`** — Script compilation and execution engine: `IScript`, `IScriptManager`, context-based execution, mock/empty implementations for testing.
- **`Converters/`** — 16 XAML value converters (enum, file size, time span, layout/thickness helpers).
- **`Native/`** — P/Invoke and interop: `Native.Win32` (Win32 API), `Native.MacOS` (NSOpenPanel, NSURL, osascript via dynamic lib loading), `FullScreenWindowControls` (inline traffic lights in macOS fullscreen — see the dedicated section above). General-purpose Objective-C wrappers belong in `CarinaStudio.AppBase.MacOS`, not here; local `NSObject` subclasses in this folder are for AppSuite-specific behavior only.

## Patterns

- **MVVM** throughout: `ViewModel<TApp>` base, Avalonia bindings, `INotifyPropertyChanged`.
- **Template Method**: `AppSuiteApplication`, `MainWindowViewModel`, `BaseProfile` all define abstract/virtual hooks (`OnLoad`, `OnSave`, `OnPrepareStarting`, etc.) for subclasses.
- **Partial classes** for platform separation of `AppSuiteApplication`.
- **Generic base classes** with `TApp : IAppSuiteApplication` type constraints propagated across the framework.
